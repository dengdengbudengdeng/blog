## 开篇介绍

在 **Python** **Web** 开发领域，**WSGI**（***Web Server Gateway Interface, Web 服务器网关接口***）长期以来一直都作为服务器、框架和应用程序之间兼容性的标准接口。它为开发者们提供了一个广阔的平台，在这个平台上涌现出了大量的自由创新。然而，随着技术的发展，特别是异步编程模式的兴起，传统的同步 **WSGI** 协议开始显现出它的局限性。

为了应对这一挑战并推动 **Python** **Web** 进一步发展，**ASGI**（***Asynchronous Server Gateway Interface, 异步服务器网关接口***）应运而生。作为 **WSGI** 的精神继承者，**ASGI** 不仅保留了其前辈的优点，更将 **Python** **Web** 带入了异步的新纪元。通过支持异步操作，**ASGI** 能够更好地满足现代互联网应用对于高性能和响应速度的需求。

总之，**ASGI** 的目标是延续 **WSGI** 的成功，并在此基础上扩展 **Python** **Web** 生态系统的边界，使之更加适应快速变化的技术环境。无论是微服务架构还是实时交互式应用，**ASGI** 都为开发者提供了更强大的工具来构建下一代的网络解决方案。

## WSGI 为何不再适用

每当提及 **Python** **Web** 开发标准这一话题的时候，人们常常会问：“为什么不直接升级 **WSGI** 协议，而是再定义一个 **ASGI** 协议呢？”这个问题在过去的多年间被反复提出。而实际上，开发者在尝试升级 **WSGI** 的过程中遇到了重重阻碍，核心问题在于 **WSGI** 所采用的单次调用接口模型并不适合处理像 **WebSocket** 这样的更复杂的 **Web** 协议。

**WSGI** 应用程序被设计为一个单一的、同步的可调用对象，它接收请求并返回响应。这种设计在处理传统的短生命周期的 **HTTP** 请求/响应模型时非常有效，但对于需要长时间保持链接的场景（例如：长轮训 **HTTP** 或 **WebSocket** 链接）则显得力不从心。例如，在 **WebSocket** 通信中，客户端与服务器之间可能会有多个消息帧的交换，这些数据帧可能在任意时间到达，这超出了 **WSGI** 一次请求对应一次响应的设计初衷。

即使我们设法将 **WSGI** 的可调用对象改为异步模式，但这依然无法解决根本问题：**WSGI** 依然只提供了一条路径来处理请求。对于那些基于事件驱动的协议（例如：**WebSocket** ，其中每收到的数据帧都可能触发新的事件），这样的设计是不够的。因为这些协议要求不仅能够处理一开始建立链接时的请求，还要能处理后续发生的各种事件或消息，这远远超出了 **WSGI** 的能力范围。

## ASGI 如何解决这些问题

面对 **WSGI** 的这些限制，**ASGI** 引入了全新的接口模型。它不仅支持异步操作，还允许应用程序以更加灵活的方式处理不同类型的 **Web** 协议。**ASGI** 的应用程序可以同时管理多个链接，并且针对每个链接都可以独立地处理来自客户端的事件或消息。这使得实现诸如 **WebSocket** 等复杂协议变得轻而易举。

此外，**ASGI** 还保留了对传统 **WSGI** 应用的支持，这意味着开发者可以在不改变现有代码的基础上逐步迁移到新的异步世界中。因此，无论是希望利用最新技术构建高性能实时应用的新项目，还是寻求优化现有系统的老项目，**ASGI** 都能提供强有力的支持！👍

## ASGI 的工作原理

**ASGI** 的设计围绕一个单一的异步可调用对象展开，它接收三个参数：`scope`、`receive`、`send` 。这种设计使得 **ASGI** 能够支持复杂的 **Web** 协议，如 **WebSocket** ，并允许应用程序处理多个入站和出站事件。

### 核心组件解析

* **`scope`**：这是一个字典，包含了关于特定连接的所有信息，例如请求的协议、方法、路径、查询参数、**HTTP** 头等。这些信息在连接建立时确定，并在整个生命周期内保持不变。
* **`receive`**：这是一个异步可调用对象，允许应用程序从客户端接收事件消息。每个接收到的消息都是一个 **Python** 字典，遵循 **预定义的** 格式。通过这种方式，应用程序可以响应各种类型的事件，比如 **WebSocket** 帧或 **HTTP** 请求体。
* **`send`**：同样是一个异步可调用对象，它让应用程序能够向客户端发送事件消息。发送的消息也以 **Python** 字典的形式表示，字典中包含了一个 **`type`** 键来标识消息的类型以及相关的数据。

此外，**ASGI** 还支持后台协程，这意味着应用程序可以在等待事件的同时执行其他任务，例如监听外部触发器（例如 **Redis** 队列中的事件），从而实现更加复杂的功能逻辑。

### 简单的应用示例

在一个最简单的形式中，**ASGI** 应用可以通过一个异步函数来编写，如下示例代码所示：

```python
async def application(scope, receive, send):
    event = await receive()
    # 处理接收到的事件
    ...
    # 发送一个事件给客户端
    await send({'type': 'websocket.send', ...})
```

在上述示例代码中，当应用程序接收到一个事件后，它可以进行相应的处理，并通过 **`send`** 函数将新的事件发送回客户端。

### 事件格式

所有发送或接收的事件都是遵循预定义格式的 **Python** 字典。这些格式是 **ASGI** 协议的基础，确保了不同服务器之间应用程序的互换性。每个事件都有一个定义好的 **`type`** 键，用于推断事件的结构。

例如，你可能会从 **`receive`** 中接收到如下 **HTTP** 请求体的事件：

```python
{
    'type': 'http.request', 
    'body': b'Hello ASGI~', 
    'more_body': False
}
```

而发送一个出站的 **WebSocket** 消息则可能是这样的：

```python
{
    'type': 'websocket.send', 
    'text': b'Hello ASGI~'
}
```

通过这些标准化的事件格式，**ASGI** 不仅简化了开发者的工作，同时也增强了不同框架与服务器之间的兼容性，为构建高效、灵活的网络应用提供了坚实的基础。

## WSGI 兼容性

**ASGI** 不仅是一个面向未来的接口标准，它还被设计为 **WSGI** 的超集，这意味着它能够完全向后兼容现有的同步 **WSGI** 应用程序。为了实现这一点，社区和相关库提供了一种定义良好的转换机制，使得 **WSGI** 应用程序能够在 **ASGI** 服务器中运行，而无需对原有代码进行大规模修改。

### 转换与包装

这一兼容性是通过一个名为 [asgiref](https://pypi.python.org/pypi/asgiref) 的库提供的转换包装器（**Adapter**）来实现的。该包装器可以将 **WSGI** 应用封装起来，使其在 **ASGI** 环境中透明地运行。具体来说，它会将传入的 **HTTP** 请求转换为符合 **WSGI** 规范的格式，并将响应结果适配回 **ASGI** 的事件模型。这样，开发者就可以利用最新的异步服务器和框架，同时继续支持他们的同步 **WSGI** 应用。

### 线程池

为了让同步的 **WSGI** 应用程序能够在异步的 **ASGI** 环境中高效运行，通常会使用线程池（**threadpool**）。线程池的作用是在后台执行这些同步任务，从而避免阻塞主事件循环。这种方式确保了即使在处理长时间运行或阻塞的操作时，整个系统的性能也不会受到影响。

通过这种方式，异步和同步代码可以在同一个进程中 **和谐共存** ，既保留了不方便修改的旧代码，又可以使用新技术。
